# Reader → NeoRead 一次性数据迁移

本分支已实现迁移、清理提示和自动化测试。正式发布前仍需使用安装包在 macOS、Windows 上人工验收。本文中的 Reader 名称只用于识别旧数据，不代表继续兼容旧桌面协议。

## 范围与入口

老用户手动下载 NeoRead。桌面只注册 `neoread://`，旧链接需手动替换；Chrome 插件继续连接 Reader 和 NeoRead。

安装版在启动正常 Go 服务、读取代理设置和打开阅读窗口之前，调用打包的 Go 程序执行迁移。开发模式不会自动读取用户的 Reader 应用数据。旧源目录为 Electron `appData` 下的 `Reader`，目标为 NeoRead 的 `userData`。

应用数据中的持久化内容完整复制，包括设置、浏览器存储、书库、原文和附件。排除可重建的 Chromium 缓存、崩溃缓存、运行锁、服务发现文件和迁移器自己的临时记录。原目录中的用户内容不做全局文本替换。

## 首次启动与后续更新

NeoRead 应用数据目录下的 `migrations.json` 保存 `schemaVersion: 1` 和 `migrations` 对象。对象中的固定键 `reader-to-neoread` 标识本次更名，与应用版本号无关。其他迁移记录会保留。

| 启动时的情况                              | 行为                                                               |
| ----------------------------------------- | ------------------------------------------------------------------ |
| 没有旧资料，也没有既有 NeoRead 书库       | 写入 `not-needed / fresh-install`，正常打开，不显示迁移弹窗        |
| 已有 NeoRead 书库或应用设置，但没有标志位 | 写入 `not-needed / existing-install`，保护现有数据，不导入旧目录   |
| 存在旧资料，尚未迁移                      | 复制、验证、启用新数据，再写入 `completed`                         |
| `copying`                                 | 校验临时目录归属，重新复制，原数据保持不变                         |
| `verified`                                | 根据文件清单与哈希继续完成尚未安装的条目；已安装条目必须与清单一致 |
| `completed` 或 `not-needed`               | 跳过迁移，即使旧 Reader 目录还存在，也不会再次复制                 |
| 记录损坏、无法读取或状态不认识            | 停止启动并显示错误，不回退到空书库                                 |

首次直接安装后续版本，也执行同一个迁移事件。迁移记录不会随版本更新重置。`completed` 只有在新数据校验与启用完成后写入。

## 书库位置与复制

先读取旧应用数据中的 `library-location.json`，以便在复制前取得实际旧书库的 `reader.lock`。若还有闲置的默认书库，也取得它的旧锁。旧 Reader 未退出时，迁移停止。

先复制应用数据，再按已读取并随副本核验的书库位置处理额外目录：

- 默认书库随应用数据迁移到 `NeoRead/library`。
- 位于旧应用数据内部的自定义书库保留相对路径，随应用数据迁移。
- 外部自定义书库完整复制到原目录的同级 `NeoRead Library`。
- 外部目标已存在、设备离线、路径重叠、配置无效时停止，不覆盖目标，也不创建空书库。
- 只存在应用设置、尚未创建书库的旧安装可以迁移设置；旧书库目录存在但数据库缺失时停止，避免把损坏资料当作空安装。

每次复制前检查目标磁盘空间，并额外预留 64 MiB；应用目录与外部书库分别检查。复制过程仍检查所有写入错误，空间不足不会删除原数据。符号链接或特殊文件会导致迁移停止，不跟随未知目录。

临时目录位于目标所在文件系统。应用目录使用 `.reader-to-neoread`，外部书库使用 `.neoread-migration-<随机ID>`。所有可重用临时目录均有归属记录。复制前后核对 SHA-256，保留文件修改时间。

## 数据库与路径

同时复制 `reader.sqlite` 及其 WAL，再在私有副本中执行完整性检查、外键检查和原文文件检查。合并已提交 WAL、关闭数据库后，将副本命名为 `neoread.sqlite`；不会直接丢弃旧 WAL 或修改源数据库。

数据库中的 `settings.reader` 转成 `settings.neoread`，已有新键优先。更新新应用数据中的书库位置。仍有效的语料索引按最终目录重新计算路径指纹；已经过期的索引不伪装成有效。较旧版本没有语料索引表时，交由正常数据库升级创建该表。

浏览器端对当前来源中可访问的批注颜色、导出选项、当前聊天会话键进行一次性转换，已有 NeoRead 值优先。存储不可写时保留未转换旧键，允许以后重试。应用使用动态本地端口，浏览器存储按来源隔离；本次复制保留所有旧浏览器存储，但不会跨来源合并这些轻量界面偏好。数据库中的笔记、聊天记录及阅读设置不受此限制。

正常服务使用 `neoread.sqlite` 与 `neoread.lock`，开发默认目录为 `.neoread`。已经使用 NeoRead 名称、数据库仍叫 `reader.sqlite` 的早期安装，在启动时从包含 WAL 的副本生成新数据库，并保留旧数据库备份；服务运行期间同时持有旧锁，避免旧程序并发打开该书库。

## 启用与中断恢复

迁移记录以临时文件写入、同步并重命名。数据验证后先记录 `verified`，再逐项重命名到正式位置；因此整个应用目录并非一次文件系统原子操作，恢复依靠持久化清单。迁移未完成时正常服务不会启动。

外部书库通过同文件系统重命名启用。应用数据每个条目启用后核对哈希；只允许备份 Chromium 启动期间生成的少数初始文件，其他目标冲突停止处理。最终写入 `completed` 后才启动正常服务。Unix 系统同步相关目录；Windows 的文件系统断电行为仍需安装包环境验证。

临时目录中的初始 Chromium 文件备份及归属记录暂时保留，便于排查中断；它们不再参与已完成迁移。原 Reader 应用数据及外部原书库在迁移阶段均不删除。

## 迁移完成后的清理提示

新书库和窗口成功打开后，仅在 `legacyCleanup.status = pending` 时提示：

> 你的数据已迁移到 NeoRead 并通过校验。
>
> 建议卸载旧 Reader App，并删除其应用数据目录，释放磁盘空间。
>
> 旧 Reader App 请手动卸载。“立即删除”仅删除显示的旧应用数据目录，不会卸载 App。

有外部书库时另外说明：外置自定义书库的旧副本不会被删除。

按钮为“稍后手动删除”和“立即删除”，默认推荐立即删除，取消按稍后删除处理。应用不会搜索或卸载 Reader App。

清理状态记录为 `kept`、`deleted` 或 `failed`，后续启动不再提示或自动重试删除。记录用户删除决定后，检查源目录归属、当前书库位置、旧书库锁与源数据哈希。旧资料在迁移后发生变化、旧 Reader 仍占用书库，或 NeoRead 正在使用源目录内的书库时，拒绝自动删除。

删除时先将旧应用目录重命名到同级 `.reader-cleanup-<ID>`，再删除该目录，避免误删旧程序随后重新创建的原路径。失败时显示可手动处理的目录。Windows 如果拒绝重命名被锁定的目录，保留旧数据并提示手动删除。清理失败不撤销已成功的迁移。

## 验证与发布验收

自动化测试使用临时目录，覆盖默认/内部自定义/外部书库、无旧数据、已有 NeoRead 数据、跳版本和重复启动、WAL 数据、旧表结构、路径指纹、损坏数据库与配置、离线设备、目标冲突、缺失原文、符号链接、旧进程锁、复制失败重试、部分启用恢复、标志位保留、清理选择和删除保护。

发布前人工检查：

1. macOS、Windows 安装版首次启动读取真实旧目录，默认及外部书库的原文、笔记、批注、设置和 Connector 配对可用。
2. 全新安装没有迁移弹窗；迁移完成后重启、升级均不重新复制旧目录。
3. 迁移完成提示中的路径正确；稍后删除不会再次弹出；立即删除仅处理旧应用目录，旧 App 与外部旧书库仍在。
4. 旧 Reader 占用、外置盘断开、权限拒绝、磁盘写满、迁移中断时，错误可理解，旧数据仍可用，重试不会启动空库。
5. 使用真实大书库和 WAL 进行中断、重启与数据核对。跨平台编译或单元测试不替代这些安装包验收。
